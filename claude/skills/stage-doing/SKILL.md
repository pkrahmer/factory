name: stage-doing
description: Stage instructions for `doing`. Preloaded into the coder agent; not invoked directly.
---

1. Claim the ticket (R6): commit with subject `ticket <id>: claim for doing`, do not push.
2. Read the ticket and the files its last log entries name (the tester's test files; on a rework round, the findings). Nothing else: not other tickets, not `FEATURE.md`, not `factory/`, not `.claude/`. If `round` is greater than 0, address exactly the listed findings, nothing more.
3. Implement as the role skill describes until `make check` is green. A test that cannot pass against the ticket (contradicts the interface, is non-deterministic) is a question (R8, R9): describe the test and the options, set `blocked: question`, clear the claim, commit as R6 says (an amend only while the claim commit is still `HEAD`), push, stop. When you arrive with the human's answer in the log and it calls for a test change, do not touch the test: append a log entry naming the test and the change in one sentence, set `stage: tests`, clear the claim, then `git add -A && git commit --amend -m "ticket <id>: doing → tests (test change approved)" && git push`, stop. The tester makes the change and sends the ticket back.
4. Commit as you go with messages `ticket <id>: feat(<layer>): <what>`. One commit per coherent change is fine.
5. Refactor, once. With `make check` green, read your own diff (`git diff main...HEAD -- . ':!factory' ':!tests'`) the way a reviewer would: rename what is unclear, simplify what is convoluted, remove duplication and dead code. Add nothing. Behaviour stays the same, tests stay untouched, `make check` is green again afterwards. Commit separately as `ticket <id>: refactor(<layer>): <what>` so the reviewer sees feature and clean-up apart. If nothing needs changing, say so in the log entry below. A restructuring beyond this ticket is a new ticket, not a refactor (R13).
6. If the human sent this round back with comments on the diff or a review's text (`human (review comment <id>, …)` and `human (review <id>, …)` entries after the demo's last hand-over), reply to each on the pull request now that your fix is committed. Start each reply with `factory: `, then `fixed in <sha>: <one line>` or `kept: <reason>`. A `kept` needs a reason the story supports (a criterion, the Interface, a decision in the log); without one it is a question (R8). A comment on the diff gets its reply in its own thread: `gh api repos/{owner}/{repo}/pulls/<pr>/comments/<id>/replies -f body="factory: …" --jq .id`. A review's text gets one `gh pr comment <pr> --body "factory: …"`.
7. Append a log entry: what you built (paths), the main design decision and the alternative you rejected, anything you noticed but did not touch. On such a round, add one indented line per comment of theirs: its id, fixed or kept, and the id of your reply.
8. Rewrite `## Assignment` only if a log entry changed the meaning of the task; then update its "as of" heading.
9. Set `stage: review`, clear the claim, commit with subject `ticket <id>: doing → review`, push. This is a normal commit, not an amend: your work commits sit between the claim commit and this one, and an amend would fold the last of them into the stage change. The claim commit stays in the history (R6).
