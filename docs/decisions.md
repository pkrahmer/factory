# Decisions

Append-only. One entry per decision, newest last. Format: date, decision, reason, what was rejected. Entries that a later one supersedes stay as they are; the log is the why of the current state, the git history and the stories are the way there.

## Built inside the first product repository (until the extraction on 2026-10-04)

- 2026-10-03 — Tests are written by a separate tester stage before implementation; the coder may not edit them. Reason: tests must encode the acceptance criteria, not the implementation. Rejected: coder writes tests, reviewer judges them.
- 2026-10-03 — `make check` is a hard gate on every stage. Reason: a check that only reports gets ignored by agents and humans alike. Rejected: advisory smells and coverage.
- 2026-10-03 — Everything on `main`, one ticket in flight, code and ticket in the same commit. Reason: with WIP 1 a branch protects against nothing and splits the snapshot in two. `main` is green at every `done` transition, red in between only for the ticket in flight; a failed ticket is reverted as a unit. Rejected: `task/<id>` branches in worktrees with a merge at the demo gate (first version of this scaffold).
- 2026-10-03 — Refactor is a step inside the coder stage (red → green → refactor), not a stage of its own. Reason: same context and warm cache; a separate agent would re-read everything and add fixed start-up cost. Rejected: a refactor stage; leaving clean-up to review findings.
- 2026-10-03 — The reviewer reads and runs checks; it writes no code, not even scratch experiments. Reason: in the first run the reviewer seeded 37 defects on its own initiative and spent most of its 23 minutes on it. Mutation testing, if wanted, becomes a tool in `make check`, not an agent habit.
- 2026-10-04 — Tickets live in one folder, `tasks/<id>-<slug>.md`, and the stage is a frontmatter field. Reason: moving files produced two of the three real defects of the first run (copy instead of move, a transition line that cannot know its own commit) and the folders held one file at a time. Rejected: a folder per stage.
- 2026-10-04 — A branch per ticket again, `ticket/<id>-<slug>`, with a draft pull request from intake on and acceptance by merging it. Reason: the human accepts from their phone, the pull request carries the whole ticket in its description, and `main` is green at every commit. The earlier reversal to main-only is superseded; worktrees stay out, one checkout and WIP 1 are enough. Rejected: acceptance at the keyboard.
- 2026-10-04 — Write lanes are enforced by a PreToolUse hook per agent (`factory/guard.py`), not by global deny rules in `settings.json`. Reason: global denies hit every session including the one developing the factory, and did not cover shell writes; the hook knows which agent is running. Rejected: deny rules on `factory/**` and `.claude/**`.
- 2026-10-04 — The dispatcher session runs on Sonnet, not Haiku. Reason: a Haiku session does not offer "always allow" on permission prompts, so every git and gh call would stop the loop for a click; the dispatcher's own reasoning is small, but it must run unattended. Rejected: Haiku with a hand-maintained allow list.
- 2026-10-04 — The dispatcher runs `factory/preflight.py` before the loop and asks the human before installing anything that is missing (git, gh, uv, make, gh login, venv, then `make check` on main). Reason: in the second run `make` was missing on the PC; the coder and the reviewer ran the Makefile's commands by hand and reported the gate green. The gate is the command, not its contents, and stage agents never work around a missing tool. Rejected: installing silently; letting stages install.
- 2026-10-04 — Questions from the tickets go to the human only through the pull request; the dispatcher never asks them in the chat. Reason: the answer must become a log entry (R4) and must survive the session; a chat answer is lost when the session ends and blocks the dispatcher while it waits. The chat remains the doorbell and the place for the preflight's install questions. The first real question (ticket 0002, a non-deterministic test) also showed that the watcher polled the pull request only at the gate, so the answer was never read; it now polls while a question is posted. Rejected: AskUserQuestion as a parallel channel.
- 2026-10-04 — A wrong test goes back to the tester: `doing → tests` once the human has approved the change; the coder never edits tests, not even with permission. Reason: the first real question was exactly this case and had no legal path. Rejected: the coder editing the test with the human's approval (blurs R9 for the reviewer).
- 2026-10-04 — The preflight probes the machine with `make lint` and a check for the shell tools the recipes call (`sh`, `grep`, `rm`, `touch`), not with `make check`. Reason: the loop restarts on whatever branch is checked out, and a ticket branch may be red on purpose (tests stage, open question); on ticket 0002 the preflight refused to start the loop over the very test the open question was about. `main` is green by construction (R10) and needs no probe. Rejected: `make check` on the current checkout.
- 2026-10-04 — The dispatcher is silent unless the human has something to do or to know, and the watcher remembers its last printed line in `.git/factory-last-line` across restarts. Reason: the monitor tool caps a watch at 30 minutes; every re-arm started a fresh watcher that repeated the current line, and the dispatcher narrated both the expiry and the repeat — two model turns with text every half hour for nothing. Merge commits are exempt from the reject check, because a pull request merge moves a ticket on `main` from `ready` to `demo` in one commit by construction. Rejected: a shorter poll interval or a longer monitor (not available); printing on every evaluation.
- 2026-10-04 — Intake runs on Sonnet, not Haiku. Reason: intake is the judgment step that decides whether a ticket is buildable, and since today it checks interface comments against criteria; Haiku needed many small tool calls (21 turns for 0001, over 25 twice for 0003) and guessed timestamps. The 1.4 minutes and ~9k tokens it saved are not worth a weaker gate. Rejected: Haiku with a larger turn budget alone.
- 2026-10-04 — Stage agents run with `permissionMode: auto`, and the allow list names the shell vocabulary the agents actually use (`echo`, `head`, `tail`, `wc`, `which`, `mkdir`, `touch`, `cd`, …, read from the transcripts). Reason: a coder on ticket 0004 died at its second tool call because one segment of a compound command (`… | head`) was not on the allow list and the prompt was rejected; a permission prompt has no reader in an unattended loop. Auto mode keeps a classifier on anything the list does not cover, and the guard hook and the deny list still apply. Rejected: `bypassPermissions` (would also skip the deny list); a session-level setting only (depends on how the session was started).
- 2026-10-04 — Version 3: no dispatcher session. A scheduler runs `factory/tick.py` every two minutes; the tick evaluates the repository and starts `claude -p "/factory <line>"` only for a line that needs a hand, headless and with `--permission-prompts none`. Reason: the long-lived session was the one part of the loop that could stall invisibly — monitor expiry every 30 minutes, skill changes only after a restart, permission prompts with no reader, a session that dies unnoticed — and it cost tokens while waiting. The tick costs nothing while idle, every run starts from the checkout, and whatever would have prompted is denied and reported on the pull request instead. Rejected: a cloud routine (clone and `uv sync` per run, no `make` there), a supervisor agent watching the session (same failure modes as the session).
- 2026-10-04 — Every stall is a pull request comment, not only the one at the attempts cap: a denied tool call, a turn limit the resume did not fix, an expired lease, a dispatcher that failed three times on one line. Reason: a stall that only the session knows about is a stall nobody knows about. Rejected: chat notifications.
- 2026-10-04 — The human in the loop is written as 'the human' in rules, skills and ticket fields (`gate: human`, `awaiting: human`), not by name. Reason: the pipeline is a pattern, not a person's tool.
- 2026-10-04 — The loop runs in a container that owns its checkout (`Dockerfile`, `compose.yml`, `factory/entrypoint.sh`); the image holds tools only, never the repository. Reason: half of the day's failures were environment failures (missing `make`, missing `pkill`, Git Bash quirks, a Windows allow list), and agents that execute model-written commands should not do so in the human's own account on their PC. Owning the checkout keeps Git as the only link between the human's working copy and the factory's (R1) and avoids slow bind mounts on Windows. The same image is meant for a NAS later, one service per repository. Rejected: bind-mounting the PC checkout; copying the repository into the image.
- 2026-10-04 — Tickets without a branch are read from `origin/main`, and the tick fetches before every evaluation; the watcher still never fetches. Reason: a ticket committed on main from the phone was invisible while the checkout sat on a ticket branch. Merged branches are judged against main, not HEAD, because between stages HEAD is the ticket branch itself.
- 2026-10-04 — What a ticket costs is recorded by the tick (one JSON line per dispatcher run: minutes, turns, tokens, dollars), summed by `factory/costs.py`, posted on the pull request when the ticket becomes ready, and written into the ticket log once, when it is closed. Reason: the numbers decide whether a ticket was worth its price and which stage to tune, and they are free — the headless run reports them. Rejected: a commit per stage (noise in the history, nothing the next stage needs).
- 2026-10-04 — The pipeline no longer knows how this project is built. Lanes (which folders an agent may write to) are `lanes:` in `factory/stages.yml`, read by the guard; the skills call only `make check`, `make lint` and `make test`, which is the whole contract between pipeline and project; test framework, layout and architecture rules live in `CLAUDE.md`, where the agents read them. Reason: first step of extracting the pipeline into a repository of its own that serves several projects; the cut is made and tested here before anything moves. Still tied to Python: the pipeline's own scripts run through `uv run`; that goes with the extraction, when they become a package installed in the image.
- 2026-10-04 — The pipeline moved out: github.com/pkrahmer/factory holds the engine, the skills, the agents and the container; this repository keeps `factory/stages.yml`, `factory/TICKET.md`, `tasks/`, `CLAUDE.md` and the Makefile contract. Pipeline decisions from here on are logged there. Reason: see the plan of the same day — several repositories, one engine, a tick that cannot live inside one of them.

## In this repository

- 2026-10-04 — The pipeline is its own repository and image. The engine (`src/factory`) is a package on the PATH; skills, agents and the allow list are installed at user level in the container; repositories carry only `factory/stages.yml`, `factory/TICKET.md`, `tasks/`, `CLAUDE.md` and a Makefile with `check`, `lint`, `test`. Reason: several repositories on one machine, one fix for all of them, and the tick that serves them cannot live inside one of them. Rejected: a Claude Code plugin (same files, one more mechanism to verify headless; can replace the user-level copy later), git submodules (every repository would still update by hand).
- 2026-10-04 — The rules are a skill (`factory-rules`) preloaded into every stage agent, not an `@` import in each repository's `CLAUDE.md`. Reason: `CLAUDE.md` describes the project; the pipeline's rules travel with the pipeline.
- 2026-10-04 — Features and stories instead of a flat `tasks/` folder (`stages.yml` version 4). A feature is a folder `factory/features/<F0001-slug>/` with a `FEATURE.md`; its stories are files `F0001-S0003-slug.md` in `drafts/`, `ongoing/` or `done/` beside it. The folder is the lifecycle: the human promotes by `git mv` into `ongoing/` (no frontmatter needed), the dispatcher archives by `git mv` into `done/` in the commit that sets `stage: done`, and a feature is complete when both `drafts/` and `ongoing/` are gone, which git shows by itself. Reason: hundreds of finished tickets in one folder hid the live ones; the feature as the bracket keeps stories where they belong and gives the human a place to write ahead. Rejected: a folder per status (a move per stage, which the watcher would have to police), a feature-level `done/` (empty folders do not exist in git; the status is derived), a `parent` field (the path says it).
- 2026-10-04 — Frontmatter reduced to the seven machine fields `stage`, `pr`, `blocked`, `comments_seen`, `claimed_at`, `round`, `attempts`. `blocked` takes `question` (written by an agent) or `asked` (the dispatcher posted it); `awaiting: human` became the stage `accept` with `gate: human` in `stages.yml`; `claimed_by` went (the stage says who), `id`, `title` and `parent` went (the path and the heading say them); the `## Transitions` section went (commit subjects carry every stage change, and git has the time). Reason: every field an agent has to maintain is a field it can get wrong.
- 2026-10-04 — Lanes are glob patterns, not folder names. Reason: `ongoing/*.md` inside every feature cannot be named as a folder, and a project can now point an agent at `app/*` or `web/src/*` without the engine knowing the layout.
- 2026-10-04 — Closing a pull request means two things by stage: at `accept` it sends the story back to the coder (round + 1); at any other stage — only reachable while a question is posted — it discards the story (R14), which the dispatcher does by moving the file on `main` back to `drafts/`, where it is still the human's untouched draft, and deleting the branch. Reason: a stalled story at `tests` has nothing to send back to a coder; the human's text should survive the discard.
- 2026-10-04 — A `docs` stage with its own agent, the documenter, between `review` and `demo`. It writes what the story's docs criterion says the reader must know afterwards (README, `docs/`), cross-reads the rest of the documentation against the diff for staleness, and sends a code-versus-docs contradiction back to `doing` as a finding. Reason: documentation needs the reader's perspective, which the author of the code does not have, and nobody but a dedicated stage will read the other documents for drift; the same argument that separates the reviewer from the coder. Rejected: documentation as a coder step (written from the author's view, never cross-read), a documenter after demo (the demo should run against the README it documents), reviewing the documentation by agent (the human reads documentation diffs best; the pull request is that review).
- 2026-10-04 — Every story ends with two fixed criteria, `make check stays green` and `docs: <what the reader must know> | none (reason)`. In-code docstrings stay with the coder and are enforced by the project's lint (`ruff` `D` rules on the interface packages); generated documentation such as `docs/openapi.json` belongs to the coder's lane and is kept current by a test. Reason: documentation that is not a criterion does not get written; a generated file is code's output, not prose.
- 2026-10-04 — The template README describes the application, not the pipeline: what it is, how to run it, where to look next, and one closing paragraph on how it is built. Reason: the repository's readers are the application's users; the pipeline has its own repository.
- 2026-10-04 — The preflight checks that every agent `stages.yml` names is installed, and its stamp carries the factory version and a hash of `stages.yml`, so a new image or a changed stage table runs it again. Reason: the first story under version 4 stalled twice on "agent type 'documenter' not found" because the container still ran the previous image while the repository's `stages.yml` already named the new stage; the stamp lived in the checkout's `.git`, which outlives a rebuild, so no preflight ran. Rejected: checking the agent at dispatch time only (the story is already claimed by then).
- 2026-10-05 — A pull request closed at `accept` without a reason does not send the coder off to guess. The dispatcher reopens it as a draft, moves the story to `doing` (round + 1) and asks on the pull request with three options: comment what should change (the coder reworks exactly that), close again to discard the story to `drafts/`, or mark ready and merge to accept it as it is. The reason is any human comment after the demo's hand-over, including one written with the close. The same question replaces the old round-cap handling at `accept`, which left the story at `accept` with the pull request closed, where the `closed` line came back on every tick and the question could never be posted. Reason: the hands-off demo run found that a silent close gave the coder a rework round with no finding to address. Rejected: a fresh question stage (the existing `blocked: asked` and the discard-on-close path already carry all three answers).
- 2026-10-05 — A restart recovers by itself. The entrypoint removes tick and git index locks at start (nothing runs before the first round, so any lock belongs to a killed run) and exports its start time; the tick turns `busy` for a claim older than that start into `expired`, so the story is retried at once instead of after the lease. The watcher and its contract are unchanged: the translation is the tick's, which alone knows the machine restarted. Reason: a restart during a stage left the tick lock behind, and every tick returned quietly for lease + 10 minutes, then the story waited out its own lease. Rejected: a shorter lease (a long coder run would expire), clearing claims in the entrypoint (writing a ticket is the dispatcher's job).
- 2026-10-05 — The dispatcher does not second-guess a line: an `expired` claim is dead even when it is minutes old, because the tick may know the machine restarted after it was made. And a run on a line whose handling always commits (`expired`, `merged`, `closed`, `reject`) that reports success but moved no branch is a failure, so it is retried and, at the third time, reported on the pull request; a restart also forgets the last handled line. Reason: in the first restart test the dispatcher computed the claim's age itself, found 36 seconds, did nothing and reported success; the tick remembered the line as handled and the story would have sat until someone committed. Rejected: letting the tick clear the claim itself (writing a ticket stays the dispatcher's job).
- 2026-10-05 — Before starting an agent the dispatcher asks GitHub for the story's pull request state: closed means the line is handled as `closed` (outside `accept`, a discard), merged as `merged`. Reason: the watcher polls a pull request only while the story waits for the human, so a pull request closed while the stages worked went unnoticed until `accept`, and every stage in between ran for nothing on a story the human had dropped. Rejected: polling every pull request in the watcher (a contract change and a GitHub call per story per tick for an event the dispatcher meets anyway).
- 2026-10-05 — The pull request body's closing line says what the human's actions do at `accept`, nothing more: merge accepts; close with a comment sends the story back with that comment as the reason; a close without one is answered with a question; a comment alone is only recorded. Reason: it used to invite "Comment to ask or answer", but no stage runs at `accept`, so a question asked there went into the log and was never answered (found in a demo run, F0001-S0004). Rejected: an agent that answers at the gate (a new stage, a change to the model).
- 2026-10-05 — Intake after an answer: the dispatcher checks out the existing ticket branch (the watcher says `main` for every `ready` story, but the question and the answer live on the branch), and intake carries an answer that changes the story into it verbatim, citing the log entry. Reason: the first answered intake question in a demo run (F0002-S0002) went through only because the agents improvised past "create the branch" and "do not improve the story". Rejected: a `<where>` from the watcher that names the branch for `ready` (a contract change for a case the dispatcher can see).
- 2026-10-05 — Failure paths are criteria, not the tester's invention. Intake asks when a rule in the Interface has no criterion for its failing side; the tester tests a stated limit on both sides of its boundary (that is what the number says) but tests nothing the criteria leave open; the reviewer checks both and names a missing failing-side criterion as a finding against the story. Reason: the tester must not decide what the product does in cases the human did not specify — that is the question loop of the reference's ticket 0008 — but a story that states only the happy path leaves the error paths untested, and the author forgets them. Rejected: letting the tester write counter-tests freely (product decisions by the wrong role); mutation testing as an agent habit (a tool in `make check` or a nightly run, when the number is wanted).
- 2026-10-05 — The template's gate grows by SAST (semgrep with vendored rule sets, beside bandit), a secrets scan (detect-secrets with a reviewed baseline), a licence allow list over the production dependencies, and, for an HTTP API, a schemathesis contract test; the factory's own `make check` lints its Dockerfile with hadolint. Silencing markers are on the project's *Not without asking* list, and the reviewer treats one without a stated reason as a finding. Reason: these are the test classes an enterprise stack covers (SAST, SCA, secrets, licence, API conformance), in shapes that run in seconds and offline; the contract test is the first check that tests behaviour no criterion named and found three schema gaps in the reference repository on its first run. Rejected: image scanning and SBOM in the gate (they need a built image or a release; feature acceptance or release stage), Dependabot updates (a story class nobody owns), branch protection on `main` (would block the dispatcher's archive commit; a decision of its own).
- 2026-10-05 — Feature acceptance: a stage `feature` with its own agent, the acceptor, runs once per feature when the last story is archived (`done/` non-empty, `ongoing/` and `drafts/` empty, no `ACCEPTANCE.md` covering that set of stories). It judges the whole against `FEATURE.md` (scope, an end-to-end feature demo, `make mutants`, what the stories noticed but did not touch, the documentation read as one, the decisions taken for the human, slow checks, cost) and writes `ACCEPTANCE.md` plus proposed stories as drafts, on `acceptance/<feature>` with a pull request; merging takes report and drafts into the feature, closing records the refusal on `main` so the acceptance is not due again. R13 becomes "nothing is *started* without the human": the acceptor proposes drafts, only the human promotes. Reason: every stage sees one story; nobody saw the feature, and observations the stages wrote down ("noticed, not touched") were lost; the mutation score belongs to a finished feature, not to every story's gate. Rejected: running it inside the dispatcher's `merged` step (long, unrestartable, no channel for the report), a feature-level `done/` marker (the report's `stories` list derives it), one draft per mutant (noise; one per coherent change).
- 2026-10-05 — Trunk-based stays: stories merge into `main` one at a time, and the feature acceptance is a verdict on the feature's status, not a gate on `main`. The human's merge of each story is the code gate; the acceptance's `outcome` (`accepted` by merge, `refused` by close) is the feature's status, shown on the board, and will be the release gate: nothing leaves dev (`main`) until its feature is accepted. A refused acceptance keeps its report on `main` (`outcome: refused`, the human's comment under the verdict) and loses only the proposed drafts; the human's comment is the brief for the stories the human writes next. Reason: by the time a feature is complete its code is on `main` by design, so "not accepted" cannot reject code and should not pretend to; what it can decide is what ships. Rejected: feature branches with stories merging into `feature/<F>` and the acceptance as the pull request to `main` (a real code gate, but story pull requests against another base, a watcher reading from feature branches, archive commits off `main`, a dev instance that sees only finished features, and merge conflicts between features — right when features run in parallel or `main` must be stable for others, which is not this factory's case).
- 2026-10-05 — Commits carry noreply addresses only. The factory's own identity defaults to `factory@users.noreply.github.com`, `.env.example` says to keep it anonymous, and `scripts/demo-check.sh` notes an author address that is not a GitHub noreply one. Reason: a repository built by the factory may be public, and an address in a commit is published with it and stays in its history.
- 2026-10-05 — The hands-off exercise became the demo: `demo/README.md` with the project skeleton and the eight stories of the clean run, `scripts/demo-check.sh` with the target as a required argument, and a hardening mode for maintainers in the same document. The exercise's log stays in the archived repository; the demo keeps its numbers as *What a run looks like*. Reason: the exercise is what shows a stranger the factory at work, with one prompt, and it needs no repository of the author's to follow.
- 2026-10-05 — The factory was republished as a new repository, starting from one commit, rather than rewriting the old history. Reason: the history carried a personal address, session links and the names of private repositories; a rewrite leaves old commits reachable through pull request refs. The way to this state stays in the archived repository; the why is in this file.
- 2026-10-05 — The dispatcher is code (`factory.dispatch`, called by the tick), not a Sonnet session following a skill. Every line's bookkeeping — archive, discard, refusal, questions, answers, `reject`, `expired`, stalls, the pull request check before a stage, the branch before an agent — is a handler with tests against a throwaway `origin` and a fake GitHub; only a `run` line starts a model, the stage agent. Reason: the three demo runs found no defect in the agents' judgement and ten in bookkeeping, five of them a model not following the protocol (second-guessing `expired`, a bullet for a log entry, wrong entry numbers) and four protocol gaps only a live run could show; and the dispatcher session cost $0.11 to $0.13 and 15 to 20 seconds every time, about 42 % of a clean story (`docs/deterministic-core.md`). A situation no handler knows raises, and the tick retries and then reports it, where a model improvised (fix 10 of the demo runs went through only that way). A stage run that ends without a stage change or a question is a stall, whatever the agent says. Rejected: a stricter dispatcher skill (the same failure class), the Agent SDK (a dependency for what the CLI does).
- 2026-10-05 — Agents are started by the tick from their files (`factory.agent`): model, tools, effort and the skills' text passed as flags (`--append-system-prompt-file`), the lane guard as a hook in a `--settings` file, a dollar budget per agent (`budget_usd`) as `--max-budget-usd`, the lease as the wall-clock limit. A run stopped by its budget is resumed once, under the session id the tick chose, to hand back. Reason: a spike with Claude Code 2.1.289 showed that `claude -p --agent <name>` ignores the agent file in print mode (no preloaded skills, no hooks, no turn limit) and that `--max-turns` no longer exists. Rejected: `--agent` (does not apply the file); no limit at all.
- 2026-10-05 — Every comment the factory posts carries a hidden marker, `<!-- factory -->`, and the factory knows its own comments by it (a `factory:` prefix still counts, for comments posted before). At the attempts cap the question says "comment anything to retry, close to stop", and any comment is a retry. Reason: the pull requests are opened with the owner's token, so the author does not tell the human from the factory; a marker that code adds cannot be forgotten, a prefix a model writes can. Whether an answer "says retry" was the dispatcher's one interpretation of free text, and the only other answer offered is a close, which is its own line. Rejected: a keyword the human must type.
- 2026-10-05 — The story's form is checked by code (`factory-check-story`, `story.check`): its place and id, `FEATURE.md` beside it, every section of the repository's `factory/TICKET.md`, an `Expect:` line after every Demo block, the criteria and the log numbered without gaps, `make check` and `docs:` as the last two criteria. The dispatcher runs it before intake, names the result in intake's task, and moves a story back to `ready` with the findings as the question when intake moves it on anyway. Intake keeps what code cannot judge: a concrete Interface, testable criteria, the failing sides, a runnable Demo, the architecture, the scope. Reason: demo-run fix 17 (intake accepted a Demo command without `Expect:`) and fix 16 (a carried-in criterion after `docs:`) were a model judging rules that have one right answer. Rejected: more emphasis in intake's skill (fix 17 was already that).
